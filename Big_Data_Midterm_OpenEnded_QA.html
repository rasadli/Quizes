2Explain the difference between capacity, throughput and latency. Give an example of each.
  • Capacity is how much data a system can store. Example: a storage cluster holds 500 TB.
  • Throughput is the rate at which data moves through or is processed by the system, per unit of time. Example: the cluster reads 2 GB/s.
  • Latency is the delay between a request and the first result. Example: a query takes 50 ms before the first row comes back.

Capacity has grown much faster than throughput, and throughput much faster than latency has improved. A single machine can no longer read all its data in reasonable time, which is why we split data and read it in parallel across many machines.

3★What does it mean that Hadoop is scale-out rather than scale-up? Give one example of each and explain how scale-out improves scalability and reliability.

Scale-up (vertical): make one machine more powerful. Example: upgrade a database server from 64 GB to 512 GB of RAM and a faster CPU.

Scale-out (horizontal): add more ordinary (commodity) machines to a cluster. Example: grow a Hadoop cluster from 10 to 20 DataNodes.

Scalability: capacity and processing power grow almost linearly as nodes are added. There is no hardware ceiling of a single machine, and commodity nodes are much cheaper than high-end servers. Work is split into tasks that run in parallel (shared-nothing architecture).

Reliability: no single worker is critical. HDFS replicates each block (default 3 copies) on different nodes, and failed tasks are re-run on other nodes. One machine failing, which is common at cluster scale, does not stop the system. With scale-up, the one big server is a single point of failure.

4★Explain how Big Data Analytics helps organisations extract insights and improve business outcomes. Give one industry example.

Big Data Analytics collects large, fast and varied data, processes it on distributed systems, and applies statistics and machine learning to it. The goal is to move from raw data to information, knowledge and decisions (the DIKW pyramid). It supports all four kinds of analytics: what happened, why, what will happen, and what to do.

Business outcomes:

  • Grow revenue: personalisation, recommendations, dynamic pricing.
  • Cut costs: forecasting, automation, predictive maintenance.
  • Reduce risk: fraud detection, credit scoring.
  • Better decisions: evidence and experiments replace gut feeling.

Example (banking): every card transaction is scored in real time by a model trained on historical fraud patterns. Suspicious transactions are blocked instantly, which reduces fraud losses and protects customers.

7Explain the difference between ETL and ELT. When would you choose each?
  • ETL (Extract → Transform → Load): data is cleaned and shaped before it lands in the warehouse. Choose it for classic on-premise warehouses, fixed schemas, expensive storage, or when sensitive data must be filtered before loading.
  • ELT (Extract → Load → Transform): raw data is loaded first and transformed inside the warehouse when needed. Choose it for modern cloud platforms (Snowflake, BigQuery) with cheap storage and elastic compute, and when you want flexibility to re-transform raw data later.

ETL needs more upfront engineering and is less flexible. ELT is more scalable and is today's default.

8★Given a dataset of users, time spent and purchases, propose a data-driven and a non-data-driven decision, and explain why the first is data-driven.

Using the past exam data (product A, 30% discount): User 1 spent 5 min (no purchase), User 2 spent 2 min (bought), User 3 spent 7 min (no), User 4 spent 5 s (no), User 5 spent 4 min (bought).

  • Data-driven: send the discount only to User 1 and User 3. They showed strong interest (long time spent) but did not buy, so price is the likely barrier. Skip Users 2 and 5 (already bought) and User 4 (5 seconds, no interest).
  • Non-data-driven: send the discount to everyone, to random users, or to whoever the manager picks by intuition.
  • Why it is data-driven: the decision is based on observed behaviour (engagement + outcome) rather than guesswork. It targets the users most likely to change their behaviour, avoids wasting discounts on people who would buy anyway, and the result can be measured (conversion rate of the targeted group).
9Describe the stages of the data science lifecycle. Why is it iterative?
  1. Business understanding: define the problem and goal.
  2. Data understanding: collect and explore available data.
  3. Data preparation: clean, transform and build features. This is usually most of the effort.
  4. Modeling: train statistical or ML models.
  5. Evaluation: check the model against business and model metrics on unseen data.
  6. Deployment: put it into use, then monitor it.

Why iterative: findings at any stage send you back. Poor data quality sends you back to preparation, a weak model back to features, and a changed business need back to step 1. Frameworks such as CRISP-DM formalise this loop.

HDFS

Lectures 4–5

11★Explain how HDFS achieves fault tolerance. What happens when a DataNode fails?

Replication: each file is split into blocks (128 MB), and each block is stored on several DataNodes (default replication factor 3). With rack awareness, one copy goes on the local rack and two on a different rack, so even a rack failure loses no data.

When a DataNode fails:

  1. DataNodes send a heartbeat to the NameNode every 3 seconds. When heartbeats stop (after about 10 minutes), the NameNode marks the node dead.
  2. From block reports, the NameNode knows which blocks that node held, and that they are now under-replicated.
  3. It tells DataNodes holding the surviving copies to re-replicate those blocks to other nodes until the replication factor is restored.
  4. Clients reading the file are sent to another replica, so reads keep working.

Checksums also detect corrupted blocks, which are then replaced from a healthy copy.

12★Explain the process of checkpointing and its purpose. What are the fsimage and the edit log?
  • fsimage: a snapshot of the entire filesystem namespace (directories, files, block mapping) saved on disk.
  • Edit log: a journal of every change (create, delete, rename) made since the last fsimage.

The NameNode keeps the namespace in memory and writes each change to the edit log. Over time the edit log grows very large.

Checkpointing merges the edit log into the fsimage:

  1. The Secondary NameNode (or the Standby NameNode in HA setups) fetches the current fsimage and edit log.
  2. It loads the fsimage into memory and replays the edits.
  3. It writes a new, up-to-date fsimage and sends it back to the NameNode.
  4. The NameNode starts a fresh, empty edit log.

This happens by default every hour or every 1 million transactions.

Purpose: keep the edit log small, make NameNode restarts fast (otherwise it would replay a huge log), and limit metadata loss.

The Secondary NameNode is not a hot backup. It only does checkpoints.

13Describe the roles of the NameNode and the DataNode. Why is the NameNode a single point of failure, and how is it mitigated?

NameNode (master): stores only metadata, in memory: the namespace (file and directory tree), file → blocks mapping, and block → DataNodes locations. It handles opens, closes and renames, decides where replicas go, and monitors DataNodes. It never stores or forwards file data.

DataNode (worker): stores the actual blocks on its local disks, serves reads and writes directly to clients, sends heartbeats and block reports to the NameNode, and copies blocks when told to.

Single point of failure: there is only one active NameNode, and without its metadata no file can be located, even though the data still sits on the DataNodes. If it crashes, the whole cluster is unusable.

Mitigation: regular checkpoints and copies of the fsimage and edit log on several disks or remote storage. In Hadoop 2+, HA runs an Active and a Standby NameNode sharing the edit log (through JournalNodes), with ZooKeeper handling automatic failover.

14Explain step by step how a client writes a file to HDFS.
  1. The client asks the NameNode to create the file. The NameNode checks permissions and that the file does not already exist.
  2. For each block, the client asks the NameNode for target DataNodes and gets a list, e.g. DN1, DN4, DN5 (rack-aware).
  3. The client opens a pipeline: client → DN1 → DN4 → DN5.
  4. The client streams data in small packets to DN1 only. DN1 stores each packet and forwards it to DN4, which forwards it to DN5.
  5. Acknowledgements flow back along the pipeline (DN5 → DN4 → DN1 → client).
  6. When a block is full, steps 2–5 repeat for the next block.
  7. The client closes the file, and the NameNode commits the metadata.

The client never sends data to the NameNode and never copies data to every DataNode itself.

15Explain step by step how a client reads a file from HDFS.
  1. The client asks the NameNode to open the file.
  2. The NameNode returns the list of blocks and, for each block, the DataNodes holding a replica, sorted by distance to the client.
  3. The client reads each block directly from the closest DataNode, streaming it.
  4. If a DataNode fails or a checksum does not match, the client switches to another replica and reports the bad block.
  5. Blocks are read in order until the end of the file, and then the client closes it.

Data never passes through the NameNode, which keeps it from becoming a bottleneck.

16Why does HDFS use large blocks (128 MB)? Why does it handle many small files poorly?

Large blocks:

  • Seek time becomes small compared with transfer time, giving high throughput for streaming reads.
  • Fewer blocks per file means less metadata in NameNode memory.
  • Fewer, larger map tasks (one split per block), so less scheduling overhead.

Small files problem: every file and block costs about 150 bytes of NameNode RAM regardless of its size. Millions of tiny files exhaust NameNode memory, and each tiny file creates its own map task, which is very inefficient. A file smaller than a block does not waste a whole 128 MB on disk; the problem is metadata and task overhead.

HDFS is also designed for write-once, read-many streaming. It is poor at low-latency reads and random updates, which is why HBase exists.

18★Write a MapReduce job: average temperature per city. Give the mapper/reducer pseudocode and the key-value pairs at each stage.

Input lines look like City, Date, Temperature, e.g. Baku, 2026-11-01, 14.

MAP(offset, line):
    city, date, temp = split(line, ",")
    EMIT(city, temp)

REDUCE(city, temps):
    sum = 0; count = 0
    for t in temps:
        sum += t; count += 1
    EMIT(city, sum / count)

The same template works for "total per key" questions (like the hospital question): the mapper emits (key, number) and the reducer sums.

19★How could a combiner improve the job above? When can the reducer be reused as a combiner, and when not?

A combiner is a "mini-reducer" that runs on each mapper's local output before the shuffle. It merges values with the same key on that node, so far fewer records are written to local disk and sent over the network.

Reusing the reducer is safe only if the operation is associative and commutative, such as sum, count, max and min. For word count, the pairs (cat,1), (cat,1), (cat,1) become (cat,3) locally, and the reducer still sums correctly.

Average is the counterexample. The average of averages is wrong when groups have different sizes: avg(avg(10, 20), avg(30)) = avg(15, 30) = 22.5, but the true average is 20. The fix is for the combiner to emit (city, (sum, count)). The reducer then adds up the sums and counts and divides once at the end.

A combiner works only on one mapper's output. It cannot merge keys across mappers, and Hadoop may run it zero, one or many times, so the result must not depend on it.

20Explain the shuffle and sort phase. What happens between map and reduce?
  1. Buffer and spill (map side): map output goes into an in-memory buffer (100 MB by default). When it is about 80% full, it is partitioned by reducer, sorted by key, optionally combined, and spilled to the mapper's local disk.
  2. Merge: the spill files are merged into one sorted, partitioned file per map task.
  3. Copy (shuffle): each reducer fetches its own partition from every mapper over the network.
  4. Merge-sort (reduce side): the reducer merges these sorted pieces so that all values for one key sit together: (key, [v1, v2, …]).
  5. The reduce function is called once per key.

Purpose: group all values for the same key together on one reducer. It is the most expensive phase, because it moves data across the network (all-to-all traffic). That is why combiners and good partitioning matter.

21Explain data locality. Why does MapReduce move computation to the data?

Data locality means running a map task on the node (or at least the rack) that already stores its input block. The scheduler asks the NameNode where the block's replicas are and prefers, in order:

  1. Node-local: same machine.
  2. Rack-local: same rack.
  3. Off-rack.

Why: the code (a JAR of a few KB) is tiny, while the data (128 MB per block, terabytes per job) is huge. Network bandwidth is the scarcest resource in a cluster. Shipping the code to the data avoids moving terabytes across the network, so jobs run faster, the network stays free for the shuffle, and the system scales.

Replication helps locality: with 3 replicas, there are 3 nodes where a task can run locally.

22Explain the difference between a block and an input split. How is the number of map tasks determined?
  • Block: a physical HDFS storage unit of a fixed size (128 MB), replicated across DataNodes.
  • Input split: a logical chunk of input assigned to one map task. It respects record boundaries: a line cut across two blocks belongs entirely to one split.

Number of map tasks = number of input splits. By default split size = block size, so one map task per block. Example: a 300 MB file with 128 MB blocks gives 3 blocks, 3 splits and 3 map tasks.

Replication does not change the number of mappers. With replication factor 3 there are 9 physical copies but still only 3 map tasks. Each split is processed once, and the replicas only give more choices for where to run it.

Inside a task, the record reader turns the split into records, and map() is called once per record.

23Why does MapReduce spill intermediate data to local disk instead of HDFS?

Why spill at all: memory is limited. Map output first collects in a RAM buffer. When the buffer fills, it must be sorted and written to disk.

Why local disk, not HDFS:

  • Intermediate data is temporary. It is deleted once the job finishes.
  • Writing to HDFS would replicate it 3 times across the network, which is expensive and pointless.
  • If a node dies and its map output is lost, the framework simply re-runs that map task from the original replicated input.

Only the final reducer output is written to HDFS, one part-r-NNNNN file per reducer.

24Explain how a partitioner decides which reducer receives a key. Give an example.

The default HashPartitioner computes reducer = hash(key) mod R, where R is the number of reducers. Every mapper uses the same function, so all pairs with the same key end up at the same reducer, which is required for correct results. Each mapper writes one partition file per reducer.

Example (R = 3, using the past exam hash values):

Keyhashhash mod 3Reducer
big30R0
data41R1
engineering22R2
careful101R1

A good partitioner spreads keys evenly. A skewed key (one very frequent word) overloads one reducer and slows the whole job. Custom partitioners can fix this or group related keys together.

  1. The client submits the job to the RM.
  2. The RM gets a container on some node and an NM launches the AM in it.

26Compare Hadoop 1 (JobTracker/TaskTracker) with Hadoop 2 (YARN). What problems did YARN solve?

Hadoop 1: a single JobTracker both managed cluster resources and scheduled and monitored every task of every job. TaskTrackers on workers had fixed map slots and reduce slots.

Problems:

  • Scalability: the JobTracker was overloaded beyond about 4,000 nodes.
  • Single point of failure: if the JobTracker crashed, all running jobs were lost.
  • Poor utilisation: idle reduce slots could not be used for map tasks.
  • MapReduce only: no way to run Spark, streaming or other frameworks.

YARN's fix: split the JobTracker's two jobs. The ResourceManager does only resource allocation, and a per-application ApplicationMaster does scheduling and monitoring for its own job. TaskTrackers became NodeManagers, and fixed slots became flexible containers. Many frameworks (MapReduce, Spark, Tez, Flink) can now share one cluster.

27★What happens when (a) the node running the ApplicationMaster fails, and (b) a worker node fails? Which component detects and which handles each?

(a) The AM's node fails:

  • The AM dies with its node.
  • Detection: the ResourceManager stops receiving the AM's heartbeats (and the NM's heartbeats).
  • Handling: the ResourceManager (its ApplicationsManager) starts a new AM attempt in a new container on another node, up to the maximum attempts (default 2).
  • The new MapReduce AM can recover completed tasks from the job history and re-run only the unfinished ones.

(b) A worker node fails:

  • Detection: its NodeManager stops heartbeating to the RM, which marks the node lost after a timeout (about 10 minutes by default). The AM also notices that its tasks stopped reporting progress.
  • Handling: the ApplicationMaster decides to re-run the failed tasks. It requests new containers from the RM.
  • Where: on healthy nodes, preferably one holding a replica of the input block (data locality).
  • Map tasks that had already finished on that node are also re-run, because their output sat on the dead node's local disk.
28Explain Dominant Resource Fairness (DRF) with an example.

Fair sharing is simple with one resource, but YARN schedules several (CPU and memory). DRF looks at each user's dominant share: the largest fraction of any single resource the user consumes. It then tries to make these dominant shares equal across users. It always gives the next container to the user with the smallest dominant share.

Example: the cluster has 9 CPUs and 18 GB RAM.

  • User A's task needs (1 CPU, 4 GB): 1/9 CPU = 11%, 4/18 RAM = 22%. A's dominant resource is memory.
  • User B's task needs (3 CPU, 1 GB): 3/9 CPU = 33%, 1/18 RAM = 6%. B's dominant resource is CPU.

DRF equalises them. Give A x tasks and B y tasks so that 4x/18 = 3y/9, under 1x + 3y ≤ 9 CPUs and 4x + 1y ≤ 18 GB. The result is A = 3 tasks (3 CPU, 12 GB, which is 2/3 of RAM) and B = 2 tasks (6 CPU, 2 GB, which is 2/3 of CPU). Both have a dominant share of 66.7%.

Properties: no user can gain by lying about their needs (strategy-proof), no user would prefer another user's allocation (envy-free), and every user gets at least what an equal split of the cluster would give them.

HBase

Lectures 9–11 · confirmed for your midterm

29Explain the HBase write path. What is the role of the WAL, MemStore and HFile, and what happens if a RegionServer crashes?
  1. The client finds the RegionServer that hosts the row's region (using the hbase:meta table) and sends the Put.
  2. WAL (Write-Ahead Log): the RegionServer first appends the change to its WAL, which is stored in HDFS and therefore replicated. This is what makes the write durable.
  3. MemStore: the change is then applied to the in-memory MemStore of the right column family (Store), kept sorted by row key. The client receives an acknowledgement.
  4. Flush: when the MemStore fills (128 MB by default), it is written to disk as a new, immutable, sorted HFile in HDFS, and the old WAL entries can be discarded.
  5. Compaction later merges the many HFiles.

RegionServer crash: MemStore contents are lost from memory, but the WAL is safe in HDFS. The HMaster detects the failure (through ZooKeeper), splits the dead server's WAL by region, and reassigns the regions to other RegionServers. These replay the WAL edits into their MemStores, so no acknowledged write is lost.

30Explain the HBase data model: row key, column family, column qualifier, versioning. Give an example table.
  • Row key: the unique identifier of a row. Rows are stored sorted by row key, so design it for your access pattern.
  • Column family: a group of related columns, declared when the table is created. Each family is stored separately (its own Store and HFiles) for storage efficiency.
  • Column qualifier: the column name inside a family. Qualifiers can be added freely at any time, and rows can have different columns (sparse).
  • Cell: (row key, family:qualifier, timestamp) → value, stored as bytes.
  • Versioning: each cell can keep multiple versions with timestamps. Reads return the newest by default.

31Describe the roles of HMaster, RegionServer and Region. How does HBase handle a RegionServer failure?
  • Region: a contiguous range of rows of a table (start key to end key). Tables start as one region and split automatically as they grow, which is how HBase scales.
  • RegionServer: a worker, usually co-located with a DataNode. It serves read and write requests for the regions assigned to it, and holds the WAL, MemStores and block cache.
  • HMaster: the coordinator. It assigns regions to RegionServers, balances load, handles RegionServer failover, and runs schema/DDL operations (create table, add column family). It is not in the read/write path.
  • ZooKeeper: tracks live servers and the active HMaster.

RegionServer failure:

  1. Its ZooKeeper session expires, and the HMaster is notified.
  2. The HMaster splits the dead server's WAL per region.
  3. It reassigns the regions to healthy RegionServers.
  4. Those servers replay the WAL edits, then serve the regions.

The HFiles are already in replicated HDFS, so only the un-flushed edits need replaying.

32Explain compaction. Why is it needed, and what is the difference between minor and major compaction?

Why: every MemStore flush creates a new HFile, and HFiles are immutable. Over time a Store has many small HFiles, and a read must check all of them, which is slow. Deletes and updates also only add new entries (delete markers, called tombstones, and new versions), so old data piles up.

Compaction merges HFiles into fewer, larger sorted files to improve read performance.

  • Minor compaction: merges a few small adjacent HFiles into one. It is quick and frequent, and does not remove deleted cells.
  • Major compaction: rewrites all HFiles of a Store into one. It permanently removes deleted cells, expired data (TTL) and versions beyond the maximum. It is heavy on disk and network, so it is often scheduled for off-peak hours.
